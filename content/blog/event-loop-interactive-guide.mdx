## One thread, many callbacks

JavaScript runs your code on one thread with one call stack. It still handles timers, network responses, and clicks without blocking, because those callbacks wait in queues until the stack is free. The event loop decides which callback runs next.

Once you know its rule, you can predict the output of any async snippet before you run it.

<Callout type="info">
  When the call stack is empty, the event loop runs every microtask in the
  microtask queue. Then it runs one task from the task queue. Then it repeats.
</Callout>

## Three structures decide the order

The event loop moves callbacks between three structures:

- **Call stack.** The stack holds the function that is running now and the functions that called it. Synchronous code runs here. The last function pushed is the first to finish (LIFO).
- **Task queue.** The queue holds callbacks from `setTimeout`, `setInterval`, DOM events, and I/O. Some articles call it the macrotask queue. The first callback queued runs first (FIFO).
- **Microtask queue.** The queue holds callbacks from `Promise.then`, `Promise.catch`, `Promise.finally`, `queueMicrotask`, and `MutationObserver`. It is also FIFO.

A microtask is not faster than a task. It has higher priority. The event loop empties the whole microtask queue before it takes a single task, and that includes microtasks queued while the queue drains.

## Example 2: callbacks that queue more callbacks

This script nests a microtask inside a timeout, and a timeout inside a microtask.

<EventLoopComplexDemo />

The output is `1`, `6`, `4`, `2`, `3`, `5`:

1. The synchronous logs `1` and `6` run first.
2. The stack is empty, so microtask `4` runs. It queues timeout `5` behind timeout `2`, which is already waiting.
3. The event loop takes timeout `2`. Inside it, the promise queues microtask `3`.
4. Timeout `2` finishes and the stack is empty again. Microtask `3` runs before the next task.
5. The event loop takes timeout `5`.

Step 4 is the one people get wrong. A microtask queued inside a task runs right after that task, before any other task, even one that was queued earlier.

## Example 3: a timeout delay is a minimum

The script queues a 1000 ms timeout and then a 0 ms timeout. It also queues a microtask and logs `Sync end`.

<EventLoopTimeoutDemo />

The output is `Sync end`, `Microtask`, `T2 ~0ms`, `T1 ~1000ms`. The script starts the 1000 ms timer first, but its callback enters the task queue only after 1000 ms pass, so `T2` runs before it.

The elapsed time that `T1` logs is 1000 or more, never less. The timer puts the callback in the task queue after the delay. The callback runs when the stack is empty and the tasks ahead of it have finished. If synchronous code keeps the stack busy for two seconds, `T1` runs after two seconds.

## What to check when you predict output

- Synchronous code runs first, top to bottom, on the call stack.
- When the stack is empty, every queued microtask runs before the next task.
- A microtask queued during a task runs before the task after it.
- `setTimeout(..., 0)` waits for a later task.
- A timeout delay is the shortest wait, not an exact time.
