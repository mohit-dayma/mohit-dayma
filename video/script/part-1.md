## 01. The processor waits for memory

**0:38.5 – 1:45.3** (67 s)

_On screen:_ Illustrative CPU vs memory speed curves. Latency ladder (Pentium M, Drepper 2007 §3.2), then the 'typical today' bars. Pipeline timeline for the hiding aside.

- `0:38.5` _(chapter card, no narration)_
- `0:40.3` Until the early nineteen nineties, a CPU core and its memory bus ran at similar speeds.
- `0:46.3` Then CPU clock speeds rose much faster than memory speeds.
- `0:50.4` Memory as fast as a CPU core can be built. But it costs orders of magnitude more, so no ordinary computer uses it for main memory.
- `0:59.4` Here are the numbers from the paper, measured on a Pentium M. A register access takes about one cycle.
- `1:05.4` The first-level data cache, L1d, takes about three.
- `1:09.3` The second-level cache, L2, takes about fourteen.
- `1:12.8` Main memory takes about two hundred and forty cycles.
- `1:16.2` So one trip to main memory costs as much as eighty loads from L1d.
- `1:20.5` On a current desktop CPU, the numbers are larger in cycles, but the shape is the same: a few cycles nearby, hundreds far away.
- `1:29.3` These costs are not always paid in full. If the processor starts a load early enough, other work continues while the load runs.
- `1:36.9` That often hides an L1d access completely. It fails when the address is only known late, for example when another instruction computes it.

## 02. Two kinds of RAM

**1:45.3 – 2:49.4** (64 s)

_On screen:_ SRAM (6 transistors) and DRAM (1 transistor + capacitor) cards; the capacitor visibly leaks and is refreshed. The four costs reveal one by one.

- `1:45.3` _(chapter card, no narration)_
- `1:47.1` Computers use two kinds of random-access memory. They differ in how one bit is stored.
- `1:52.4` Static RAM, or SRAM, stores a bit in a circuit of six transistors. It is fast, but each bit takes a lot of chip area and constant power.
- `2:01.3` Dynamic RAM, or DRAM, stores a bit as charge in a capacitor, guarded by one transistor. It is much smaller, and packs densely on a chip.
- `2:10.2` That small size has four costs.
- `2:12.8` First, the capacitor leaks. Every cell must be refreshed, typically every sixty-four milliseconds.
- `2:19.3` Second, reading a cell drains it, so the value must be written back after every read.
- `2:24.4` Third, a cell holds only tens of thousands of electrons, so a sense amplifier must detect whether it holds a zero or a one.
- `2:32.1` Fourth, a capacitor does not charge or drain instantly, and that wait limits how fast DRAM can respond.
- `2:38.5` Cost decides the outcome. Main memory is DRAM because it is cheap per bit. Caches are SRAM because they must be fast, and they are small because SRAM is expensive.

## 03. DRAM reads a whole row at a time

**2:49.4 – 4:12.3** (83 s)

_On screen:_ A DRAM bank: rows, row buffer, activation, column reads, precharge. Cost table for module timing 2-3-2 (CL / tRCD+CL / tRP+tRCD+CL). Deep Dive aside: 11:1 core/bus clock ratio. Since-2007 note.

- `2:49.4` _(chapter card, no narration)_
- `2:51.2` A DRAM chip arranges its cells in a grid of rows and columns. A read happens in two steps.
- `2:57.3` First, row activation. The chip copies the entire row into its sense amplifiers. That copy is the row buffer, and the row is now open.
- `3:06.2` Second, the column read. The chip returns data from the open row.
- `3:10.3` A read from the row that is already open needs only the column step. With the paper's example module, that costs two bus cycles.
- `3:18.3` If no row is open, the chip must activate one first: three more cycles.
- `3:23.0` A read from a different row is worst. The open row must be closed, which is called precharge, before the new one is activated: seven cycles in total.
- `3:32.2` So DRAM rewards sequential access. Once a row is open, the controller can read a burst of consecutive words without a new address.
- `3:40.0` Caches use this. They always fetch memory in fixed blocks that one burst can fill.
- `3:45.3` A short aside: the memory bus is also slower than the core. In the paper's example, a 2.933 gigahertz Core 2 runs eleven cycles for every bus cycle, so each bus cycle of waiting costs the core eleven.
- `3:58.8` Since 2007, DDR2 has given way to DDR4 and DDR5. Bandwidth has grown many times over, but latency in nanoseconds has changed much less, because the cell physics has not changed.

## 04. Caches exploit locality

**4:12.3 – 5:31.4** (79 s)

_On screen:_ Temporal and spatial locality animations. The 200- vs 15-cycle worked example with animated bars (2,000,000 vs 168,500 cycles, 91.5%). 4 MB vs 4 GB drawn to scale.

- `4:12.3` _(chapter card, no narration)_
- `4:14.1` The processor manages its small SRAM automatically, as a cache. A cache holds copies of recently used memory, and programs do not need to know it exists.
- `4:23.5` This works because most programs show locality.
- `4:26.7` Temporal locality: data used now is likely to be used again soon. Loops are the typical example.
- `4:33.0` Spatial locality: data near recently used data is likely to be used soon. Walking an array is the typical example.
- `4:40.1` The paper gives a simple calculation. Assume main memory costs two hundred cycles, and the cache costs fifteen. A program uses one hundred data elements, one hundred times each.
- `4:51.0` With no cache, that is ten thousand accesses at two hundred cycles each: two million cycles.
- `4:56.7` With a cache, the first use of each element costs two hundred cycles, and the other nine thousand nine hundred cost fifteen. That is one hundred sixty-eight thousand five hundred cycles.
- `5:06.9` That is ninety-one and a half percent less time spent on memory.
- `5:10.9` The limit is size. In the paper's experience, a cache was about one thousandth the size of main memory: four megabytes of cache with four gigabytes of RAM.
- `5:20.6` The data a program uses during a period is called its working set. If the working set fits in the cache, the cache works well. If not, the cache must keep choosing what to evict.

## 05. The cache hierarchy

**5:31.4 – 6:25.7** (54 s)

_On screen:_ Two cores with hardware threads, L1d/L1i, L2 (shared, then split into private L2s for 'today'), L3, main memory. Inclusive vs exclusive.

- `5:31.4` _(chapter card, no narration)_
- `5:33.2` Making one cache bigger would also make it slower, so designers added levels, each larger and slower than the one before.
- `5:40.4` L1 is split in two: L1d holds data, and L1i holds instructions. It is the smallest and fastest level.
- `5:48.4` L2 is larger and slower. In 2007 it was often shared between cores.
- `5:53.9` L3 is larger again, and shared by all the cores on a chip.
- `5:58.3` Hardware threads on one core share that core's L1. Cores share the higher levels. Separate processors share no caches at all.
- `6:05.8` A level can be inclusive, where every line in L1d is also in L2. Or exclusive, where a line lives in only one level. In 2007, Intel used inclusive caches, and AMD used exclusive ones.
- `6:19.1` Today, most designs give each core a private L2, and share a large L3 between cores.

## 06. Caches store lines, not bytes

**6:25.7 – 7:36.8** (71 s)

_On screen:_ A 64-byte line loads when one byte is needed. A 32-bit address split into tag / set / offset with cache-model splitAddress for the paper's 4 MB 8-way cache.

- `6:25.7` _(chapter card, no narration)_
- `6:27.5` A cache does not store single bytes. It stores cache lines: blocks of consecutive bytes, sixty-four bytes on most current processors.
- `6:36.0` There are three reasons. Each entry needs a tag that records which memory it holds, and a tag per word would cost as much as the data.
- `6:44.2` Neighbouring bytes are likely to be used soon anyway. And DRAM delivers a burst of consecutive words cheaply.
- `6:51.0` So when the processor needs any byte, it loads the whole line. To change four bytes, it first loads the whole line too.
- `6:58.4` To find a line, the processor splits the address into three fields.
- `7:02.6` The lowest bits are the offset: the byte's position inside the line. A sixty-four byte line needs six bits.
- `7:09.2` The middle bits are the set index. They choose which set of the cache the line belongs to.
- `7:14.2` The remaining high bits are the tag. It is stored with the line, so the cache can tell apart the many addresses that share a set.
- `7:21.3` For the paper's four megabyte, eight-way cache, there are eight thousand one hundred ninety-two sets, so thirteen set bits.
- `7:28.4` The sizes are tied by one formula: cache size equals line size, times associativity, times the number of sets.

## 07. Associativity: where a line can go

**7:36.8 – 8:34.9** (58 s)

_On screen:_ Fully associative, direct-mapped and 2-way layouts of the same 8 lines, with the slots an incoming line may use. LRU eviction in a 4-way set (cache-model simulate).

- `7:36.8` _(chapter card, no narration)_
- `7:38.6` Associativity is the number of places in the cache where a given line may be stored. There are three designs.
- `7:44.8` Fully associative: any line can go in any slot. To find a line, the cache must compare its tag against every slot at once.
- `7:52.5` A four megabyte cache has sixty-five thousand five hundred thirty-six slots. That is far too many comparators, so fully associative caches only work when they are tiny, like some TLBs.
- `8:03.7` Direct-mapped: each line can go in exactly one slot. One comparator is enough, so it is fast and cheap.
- `8:10.4` But two addresses that map to the same slot keep evicting each other, while other slots sit empty. This is called a conflict miss.
- `8:18.0` Set-associative: the cache is divided into sets, and each set has a few slots, called ways. The set index picks a set, and the cache compares the tags of all its ways at once.
- `8:28.5` When a set is full, the cache evicts a line. The usual policy evicts the least recently used one.

## 08. A tiny cache, step by step

**8:34.9 – 10:17.9** (103 s)

_On screen:_ The blog simulator, replayed with cache-model: sequential scan, reuse, and conflicting arrays in direct-mapped, 2-way and 4-way. Then the paper's gcc results (§3.3.1).

- `8:34.9` _(chapter card, no narration)_
- `8:36.7` Here is the simulator from the blog post. The cache holds eight lines of sixteen bytes: one hundred twenty-eight bytes in total. Only the associativity will change.
- `8:46.2` First, a sequential scan of sixteen integers, through a direct-mapped cache.
- `8:50.9` The first read misses and loads sixteen bytes. The next three integers are already in that line, so they hit. The pattern repeats.
- `8:58.7` Four misses and twelve hits. That is spatial locality.
- `9:02.2` Next, reuse. The loop reads eight integers, three times over.
- `9:06.6` The first pass loads two lines. Every later pass finds them in the cache.
- `9:11.2` Two misses, then hits for the rest. That is temporal locality.
- `9:15.2` Now the hard case. The loop computes a of i equals b of i plus c of i, and the three arrays are one hundred twenty-eight bytes apart, exactly the cache size.
- `9:24.8` In a direct-mapped cache, all three arrays map to set zero. Every access evicts the line the next access needs.
- `9:32.2` Twelve accesses, twelve misses. And the dirty lines of a are written back over and over.
- `9:37.3` With two ways, it is no better. Three lines compete for two ways, and LRU always evicts the line that is needed next.
- `9:44.7` With four ways, all three lines fit in one set.
- `9:47.9` Three misses, then nine hits. Same capacity. Very different result.
- `9:52.6` The paper measured this on a real workload, a gcc compile, in a simulator. For an eight megabyte cache, going from direct-mapped to two-way cut misses by almost forty-four percent.
- `10:03.0` Each further doubling helped less. Above eight ways, the gains for a single-threaded program were small.
- `10:09.3` But when threads or cores share a cache, each one effectively gets only a fraction of the ways. So shared caches need higher associativity.

## 09. Writes: write-back and dirty lines

**10:17.9 – 11:17.4** (59 s)

_On screen:_ Write-through vs write-back counters on a one-line cache (cache-model). Writeback counts from the conflicting-arrays run. Write-combining, uncacheable, coherence rules.

- `10:17.9` _(chapter card, no narration)_
- `10:19.7` A cache must behave as if it were not there. After a write, every later read must see the new value.
- `10:26.0` Write-through sends every write to main memory immediately. Memory is always up to date, but the traffic is high.
- `10:32.8` Write-back only updates the cache, and marks the line dirty. The line is written to memory when it is evicted.
- `10:39.3` Most memory is cached this way, because it avoids most of that traffic.
- `10:43.8` In the conflicting-arrays run, each eviction of a dirty a line cost an extra write to memory. The direct-mapped cache wrote back three times. The four-way cache, not once.
- `10:53.7` Two other policies apply to special address ranges. Write-combining gathers several writes before sending them, for memory such as graphics cards. Uncacheable memory is never cached at all, for device registers.
- `11:05.8` With more than one core, write-back needs one more thing: cache coherence. A dirty line is present in only one cache. Clean copies can be in any number. Part five covers how this is enforced.

## 10. Which address does the cache use?

**11:17.4 – 12:22.2** (65 s)

_On screen:_ Virtual -> translation -> physical. The paper's 2007 answer. VIPT: the 32 KB 8-way L1d's set and offset fit the 12-bit page offset.

- `11:17.4` _(chapter card, no narration)_
- `11:19.2` Programs use virtual addresses, and the processor translates each one to a physical address. Which one should the cache use?
- `11:26.6` Virtual addresses are not unique. The same address means different memory in different processes. Physical addresses avoid that, but translation takes time.
- `11:35.7` In 2007, the paper's answer was this. L1 caches used virtual addresses, because with a latency of about three cycles, there is no time to translate.
- `11:45.6` L2 and larger caches used physical addresses. They are slower, so translation finishes in time.
- `11:52.2` Today, L1 data caches on x86 use both. The virtual address picks the set, and the physical address is the tag.
- `12:00.0` This works because, for a thirty-two kilobyte, eight-way cache, the set index and offset fit exactly in the low twelve bits. Those bits are the offset inside a four kilobyte page, and translation does not change them.
- `12:12.9` A program cannot choose its physical addresses. The paper's advice is to use each memory page completely, and to use larger pages where they make sense.

## 11. What changed since 2007

**12:22.2 – 13:00.7** (38 s)

_On screen:_ 2007 vs today table.

- `12:22.2` _(chapter card, no narration)_
- `12:24.0` The concepts in this video still describe current hardware. A few details have changed.
- `12:29.3` The memory controller now sits on the CPU. The Northbridge and the front-side bus are gone.
- `12:35.0` DDR5 has replaced DDR2. Bandwidth is much higher, but latency in nanoseconds has improved far less.
- `12:42.6` Most designs have a private L2 per core, and a large shared L3.
- `12:47.3` Sixty-four byte lines are still standard on x86. Some ARM designs, including Apple's, use one hundred twenty-eight bytes.
- `12:55.1` And replacement policies approximate LRU, instead of tracking it exactly.

## 12. What to remember

**13:00.7 – 13:40.7** (40 s)

_On screen:_ Seven takeaways.

- `13:00.7` _(chapter card, no narration)_
- `13:02.5` Main memory is DRAM because it is cheap. Caches are SRAM because they are fast.
- `13:08.2` DRAM is fastest when reads stay within an open row.
- `13:12.3` Caches work because of locality, and only while the working set fits.
- `13:16.8` Caches move whole lines, usually sixty-four bytes.
- `13:20.3` An address splits into tag, set index, and offset. Addresses a multiple of sets times line size apart compete for the same set.
- `13:28.4` Set-associative caches limit conflict misses. Beyond about eight ways, extra ways help one thread very little.
- `13:35.6` And write-back caches mark lines dirty, and write them to memory on eviction.
